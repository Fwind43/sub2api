# Independent MiniMax H3 implementation (local only)

Dedicated POST /v1/minimax/videos, GET /v1/minimax/videos/:id and /:id/content. Existing /v1/videos creation/status/content dispatch to H3 for MiniMax groups. Exact video model MiniMax-H3. JSON only, single video, duration 4-15 (default 6), resolution 480p/720p/1080p (default 720p). Idempotency-Key is scoped to API key; payload mismatch conflicts.

Migration 251 stores ownership, original account, upstream ID, generation/delivery/billing states, create-time group/subscription and cost quote. Worker starts through DI and stops before infra cleanup. PostgreSQL leased polling survives restart; create ambiguity becomes submission_unknown and is never automatically resubmitted. Original account is used for poll/download. Shared usage ledger receives stable minimax-h3:<task-id> identity. Only verified bounded MP4 content can settle; status strings and JSON URLs alone cannot bill. Cost is frozen at creation, not re-priced on retries. No Redis dependency for ownership/claims.

Limits: no balance reservation/release implemented; shared ledger has no dedicated safe reservation integration here. No promise of affordability between submission and settlement. Unknown submissions require operator reconciliation; no admin reconciliation endpoint added. MP4 checks are structural (ftyp/moov/mdat), not codec decoding or duration validation. Binary is re-fetched on download, not archived; upstream retention is required. Content limit 128 MiB. Redirects are disabled, so redirect-only providers are unsupported. Poller processes one task per tick. Existing legacy Grok/mmh3 lookups are not rewritten. New H3 creation through Grok is rejected.

Platform/UI: MiniMax accounts can select credentials.account_mode=h3 with API-key/custom-URL validation; MiniMax M text mode is preserved. Dedicated H3 scheduler capability prevents selection of text-only accounts. Composite routing accepts MiniMax targets, and h3-prefixed task lookups dispatch to H3 independently of the current target platform. Creation requires durable billing storage and rejects simple mode. Settlement uses the frozen user/video and account multipliers and checks task owner/key/group identity; it cannot fall back to legacy non-idempotent billing.

Verification boundary: source inspection, gofmt and git diff --check only. Tests were added but not run. No build, generation, migration execution, production access, paid API call, commit or push performed during this implementation. Wire wiring was updated manually; compilation, lifecycle recovery, ledger idempotency and frontend behavior remain unverified at runtime. Existing production groups/accounts and legacy tasks were not migrated. This is a local implementation, not a deployment or a guarantee that a charged video will remain downloadable: there is no permanent artifact archive.
